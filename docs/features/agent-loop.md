# ツール実行ループ

利用者の指示を LLM へ送り、LLM が指定したツールを実行し、その結果を会話履歴へ
足して送り直す反復である。本製品の中核であり、ほかの機能はこの反復の内側か、
反復に渡す材料を作る側に置かれる。

## 目的

| 満たす要件                                             | 内容                                                                   |
| ------------------------------------------------------ | ---------------------------------------------------------------------- |
| `FR-LOOP-01` `FR-LOOP-02` `FR-LOOP-03`                 | 反復を回し、完了の応答で終える。実装は明示的なスタックによる           |
| `FR-LOOP-04` `FR-LOOP-05` `FR-LOOP-06`                 | 中断を受け付け、応答の断片を種類別に振り分け、ツールの実行を直列に保つ |
| `FR-LOOP-07` `FR-LOOP-08` `FR-LOOP-09` `FR-LOOP-10`    | 失敗したときの再試行と、止めるべきときの打ち切り                       |
| `FR-LOOP-11` `FR-LOOP-11a` `FR-LOOP-11b` `FR-LOOP-11c` | 応答が来ないまま留まらない                                             |
| `FR-LOOP-12` `FR-LOOP-12a`                             | サブタスクへの委譲と、その承認                                         |
| `FR-LOOP-13` `FR-LOOP-14` `FR-LOOP-15`                 | 送信の間隔、リクエストの数、費用の上限                                 |
| `FR-LOOP-16` `FR-LOOP-16a` `FR-LOOP-16b`               | 作業項目の一覧と、完了の条件                                           |
| `FR-LOOP-17` `FR-LOOP-17a`                             | 利用者への質問と、その自動承認                                         |
| `NFR-USA-04` `NFR-USA-04a`                             | 実行中であることと、再試行の待機の残りを画面へ出す                     |
| `NFR-PERF-02` `NFR-REL-04`                             | 応答の待機に上限を設け、無応答のまま留まらない                         |

ユースケースは UC-01（指示を出す）と UC-12（中断する）。
反復をステップに分けた説明は [architecture.md](../architecture.md) の 4 節にある。

## 方式

実装は `src/core/task/`。`Task` は公開の窓口だけを持ち、状態は collaborator が、
手続きは `run*` の関数モジュールが持つ。

### 反復はスタックで進める

`runRecursiveClineLoop` はスタックが空になるまで繰り返す。関数の再帰にすると、長い反復で
呼び出しの段数が積み上がる。中断の確認と、連続した失敗の上限の判定は、この層で行う。

### 待機の打ち切りは、中断の要求に依存させない

OpenAI の SDK を経由したリクエストでは、中断の要求が下層の通信へ伝わらない接続先が
ある。そこで `Promise.race` でタイマーと競わせ、**拡張の側が待つのをやめる**方式にした。
中断の要求も併せて出すが、その成否に結果を依存させない。

タイマーは呼ぶたびに張り直すので、断片と断片の間隔にも効く。設定が 0 のときは
ウォッチドッグを張らない。`setTimeout` に `undefined` を渡すと遅延 0 として即座に
発火するため、そのまま渡すと上限を外した利用者の通信が必ず失敗する。

### 失敗の扱いを 3 つに分ける

| 種類         | 扱い                                               |
| ------------ | -------------------------------------------------- |
| API のエラー | 指数バックオフで再試行する。待機の残りを画面へ出す |
| 空の応答     | 猶予の回数まで再試行する                           |
| ツールの失敗 | 連続した回数を数え、上限で反復を止めて利用者へ渡す |

同じツールを同じ引数で繰り返した場合も止める。再試行では抜けられないためである。

## 制約

- 反復の 1 周は、必ず LLM への 1 リクエストを伴う。ツールの結果だけを内部で処理して
  次のツールへ進む経路は持たない。
- ツールの提示と実行は再入を禁じる。並行して実行すると、差分ビューと承認の対応が崩れる。
- 費用の上限は、接続先が使用量を返す場合にだけ数えられる。返さない接続先では
  リクエストの数の上限だけが効く。

## 危険なところ

- **待機の上限を 0 にした利用者の通信を壊しやすい。** 0 は「上限を設けない」であり、
  「直ちに打ち切る」ではない。上限の値をそのままタイマーへ渡す実装へ戻さない。
- **中断の要求が効かない接続先がある。** 中断の要求だけに頼る実装へ戻すと、応答の
  来ない接続先でタスクが終わらなくなる。
- 連続した失敗の上限を 0 にすると、上限の判定が働かない。設定の下限を確かめる。

## 確かめ方

| 何を                           | どこで                                                       |
| ------------------------------ | ------------------------------------------------------------ |
| 反復が完了で終わること         | `apps/vscode-e2e/src/suite/round-trip.test.ts`               |
| ツールの副作用が会話へ戻ること | `apps/vscode-e2e/src/suite/tool-effects.test.ts`             |
| 失敗したときの振る舞い         | `apps/vscode-e2e/src/suite/failure-paths.test.ts`            |
| 応答の来ない接続先で終わること | `src/api/providers/__tests__/openaiHang.integration.spec.ts` |
| 上限 0 で即座に失敗しないこと  | `src/api/providers/__tests__/openai-timeout.spec.ts`         |
| 再試行の間隔が伸びること       | `src/core/task/__tests__/ApiRequestTimingController.spec.ts` |
| 連続した失敗の上限             | `src/core/task/__tests__/checkMistakeLimit.spec.ts`          |

## できていないこと

- 費用の上限は、使用量を返さない接続先では効かない（`FR-LOOP-15`）。
- 中断の要求は断片の境界でしか確認しない。1 つの断片の処理が長い場合、中断までの
  待ち時間が伸びる（`FR-LOOP-04`）。
