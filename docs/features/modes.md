# 役割モード

LLM に与える役割文と、使用できるツールグループの組である。**自律モードとは別の
仕組みで、こちらはプロンプトを決める。**

## 目的

| 満たす要件                              | 内容                                                        |
| --------------------------------------- | ----------------------------------------------------------- |
| `FR-MODE-01` `FR-MODE-01a` `FR-MODE-02` | 組み込みを 2 件とし、差を役割文だけにする。持つ項目を定める |
| `FR-MODE-03`                            | 変えられるのは利用者だけとする                              |
| `FR-MODE-04` `FR-MODE-05`               | 役割文の上書きと、モードごとの接続先の割り当て              |
| `FR-MODE-06`                            | モードごとのルールとスキル                                  |
| `FR-MODE-07`                            | 実在しないモードが保存されていた場合の解決                  |
| `FR-MODE-08`                            | モードの定義の書き出しと読み込み                            |
| `NFR-REL-06`                            | 解決できないモードでも、ツールを使える状態で起動する        |

ユースケースは UC-18（役割モードごとに接続先を変える）。

### 扱わないもの

| 対象                           | どこにあるか                               |
| ------------------------------ | ------------------------------------------ |
| 自律モード（権限の側）         | [approval.md](approval.md)                 |
| ツールを提示するかどうかの判定 | [tools.md](tools.md)                       |
| ルールとスキルの探索           | [extension-points.md](extension-points.md) |

## 方式

定義は `packages/types/src/mode.ts` の `DEFAULT_MODES`。

### 2 件の差は役割文だけにする

| モード     | 役割                                                                 |
| ---------- | -------------------------------------------------------------------- |
| `code`     | コードを書き、直し、作り替える                                       |
| `research` | 調べて動かす。記録と診断を集め、設定を変える。応用のコードは書かない |

ツールグループは read・edit・command・mcp で同一である。`research` が edit を持つのは、
設定ファイルを変えるためである。

**モードを 2 件に絞ったのは、役割の軸と権限の軸が混ざっていたためである。** Roo Code は
architect・ask・debug・orchestrator の 4 件を持っていた。モードを切り替えると、
役割だけでなく権限も変わった。
権限は自律モードへ移し、役割だけを残した。計画の立て方の指示は、自律モードの `plan` が
持つ。

### 変えられるのは利用者だけとする

モードを切り替えるツールは持たない。GitHub Copilot と同じく、役割の選択は利用者の
操作に限る。

### 実在しないモードは解決してから使う

保存された設定に、削除済みのモードの名前が残っていることがある。判定の関数は解決
できないモードに対して偽を返すため、常時利用のツール以外がすべて拒否される。
**型検査もテストも成功したまま拡張が動かなくなる。** 既定値へ黙って置き換える実装ではなく、
実在するモードへ解決してから使う。

## 制約

- ユーザー定義のモードは持たない（`requirements.md` の 1.6）。文面の調整は役割モードの
  設定画面と `AGENTS.md` で行う。
- モードごとのルールとスキルは、名前の接尾辞で分ける。
- モードごとの接続先の割り当ては、プロファイルの名前で持つ。プロファイルを消すと
  割り当ても外れる。

## 危険なところ

- **`?? 既定のモード` のように検証せずに受け入れる実装へ戻さない。** 解決できないモードを
  そのまま使うと、ツールが 1 つも使えない状態になる。
- モードを足すときは、そのモード用のルールとスキルの探索も併せて確かめる。

## 確かめ方

| 何を                      | どこで                                                         |
| ------------------------- | -------------------------------------------------------------- |
| 組み込みが 2 件であること | `packages/types/src/__tests__/mode.spec.ts`                    |
| 実在しないモードの解決    | `src/core/webview/__tests__/buildState.mode.spec.ts`           |
| モードごとの接続先        | `src/core/webview/__tests__/ClineProvider.sticky-mode.spec.ts` |
| 件数が文書と合うこと      | `scripts/check-docs.mjs`                                       |

## できていないこと

- 2 件の差が役割文だけであり、ツールの範囲では区別していない（`FR-MODE-01a`）。
