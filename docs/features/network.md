# 外部通信と proxy

**既定の外部通信は、利用者が設定した LLM への 1 本だけである。** 通信先が増えるのは、
利用者が明示的に有効にした場合に限る。

## 目的

| 満たす要件                                                                   | 内容                                                                  |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `FR-NET-01` `FR-NET-02` `FR-NET-03`                                          | 通信の方式                                                            |
| `FR-NET-10` `FR-NET-10a` `FR-NET-11`                                         | 通信先を数えられる状態に保つ                                          |
| `FR-NET-12` `FR-NET-12a` `FR-NET-12b` `FR-NET-12c` `FR-NET-12d` `FR-NET-12e` | proxy の解決                                                          |
| `FR-NET-12a1` `FR-NET-13a`                                                   | SOCKS の名前の解決は proxy 側で行う。スキルの取得は解決だけを共有する |
| `FR-NET-13` `FR-NET-14`                                                      | proxy を通らない経路と、開発時の中継                                  |
| `NFR-PRV-01` `NFR-PRV-02` `NFR-PRV-03` `NFR-PRV-04`                          | テレメトリを持たず、通信先を限る                                      |
| `NFR-PERF-06`                                                                | proxy の接続を宛先ごとに再利用する                                    |

### 扱わないもの

| 対象                   | どこにあるか                     |
| ---------------------- | -------------------------------- |
| LLM への要求の形       | [provider.md](provider.md)       |
| MCP サーバの接続の管理 | [mcp-servers.md](mcp-servers.md) |

## 方式

proxy の解決は `src/utils/proxyDispatcher.ts` の 1 か所に置く。LLM の呼び出し・疎通の
確認・`web_fetch` の 3 つがここを通る。

### 通信先の数え方

| 経路                  | 既定                           |
| --------------------- | ------------------------------ |
| LLM のエンドポイント  | 通信する                       |
| `web_fetch`           | 通信しない。有効にしたときだけ |
| リモートの MCP サーバ | 通信しない。設定したときだけ   |
| コードインデックス    | 通信しない。有効にしたときだけ |
| 起動時のモデルの一覧  | 取得しない                     |
| 利用状況の送信        | 持たない                       |

**「外部通信は LLM だけ」と書くときは、明示的に有効にした場合の例外を併せて書く。**
例外を書かないと、事実と食い違う。

### proxy の優先順位

1. プロバイダプロファイルごとの指定（継承・直結・個別の指定の 3 種類）
2. VS Code が proxy を自前で解決している場合は、独自の proxy を重ねない
3. VS Code の設定
4. 環境変数

**2 を飛ばすと、認証付きの proxy を経由しないと届かない接続先が全部失敗する。** VS Code は
認証と自動設定を自前で扱う。そこへ独自の proxy を重ねると、その解決を上書きしてしまう。
ただしプロファイルで明示した場合は、利用者の意図を優先して 2 より前に上書きする。

### SOCKS は自前で組む

HTTP の proxy は undici の機能で足りるが、SOCKS には対応していない。SOCKS で張った
ソケットを undici へ渡す形にする。

接続の解決は宛先ごとに保持する。1 つだけ保持する形にすると、SOCKS 経由のモデルと
直結のモデルを交互に使うたびに作り直すことになる。

## 制約

- リモートの MCP サーバは、この解決を通らない。別の経路で接続する。
- Node の標準の通信は、環境変数の proxy を自動では読まない。明示的に渡す。
- `NO_PROXY` に対応しない。宛先ごとの除外は、プロファイルごとの直結の指定で代える。

## 危険なところ

- **「すべての外部通信はこの 1 か所を通る」と書く前に、経路ごとに確かめる。**
  以前この主張を書いたが、リモートの MCP だけが通っていなかった。
- VS Code が proxy を管理しているかどうかの判定を外すと、認証付きの proxy の環境で
  すべての通信が失敗する。

## 確かめ方

| 何を                           | どこで                                                                  |
| ------------------------------ | ----------------------------------------------------------------------- |
| 優先順位の解決                 | `src/utils/__tests__/proxyDispatcher.spec.ts`                           |
| プロファイルごとの指定         | `src/utils/__tests__/proxyDispatcher.perModel.spec.ts`                  |
| SOCKS の経路                   | `src/utils/__tests__/socksDispatcher.spec.ts`                           |
| 通信が解決を通ること           | `src/utils/__tests__/fetchThrough.spec.ts`                              |
| 疎通の確認が同じ解決を使うこと | `src/api/providers/__tests__/testOpenAiConnection.proxy-source.spec.ts` |

## できていないこと

- リモートの MCP が proxy の解決を通らない（`FR-NET-13`）。
- `NO_PROXY` に対応しない（`FR-NET-12b`）。プロファイルごとの直結の指定で代えており、
  対応の予定は無い。
