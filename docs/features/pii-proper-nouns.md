# 固有名詞の検出（第 2 層）

## 目的

辞書に書かれていない固有名詞を、前後の文から判定して伏せる（`FR-PII-21`）。

[pii-masking.md](pii-masking.md) の第 1 層は、形の決まった値（メールアドレス・電話番号・
カード番号）と、利用者が挙げた語を伏せる。**数え上げられるものしか伏せられない。**

固有名詞はそこから漏れる。氏名は増え続け、書き出せない。取引先の社名も、辞書に入れた
分しか該当しない。町域（`神南` `丸の内`）の一覧は第 1 層が持たない。施設名には手段が無い。

第 1 層は「推定に頼る検出は入れない」という決めごとを持つ。**固有名詞だけがその例外**で
ある。ほかに手段が無く、後述の実測で誤検出が確度で切れることを確かめたためである。

| 要件                                   | 扱う範囲                           |
| -------------------------------------- | ---------------------------------- |
| `FR-PII-21`〜`FR-PII-21c`              | 何を判定し、何を伏せるか           |
| `FR-PII-21d` `FR-PII-21e` `FR-PII-21f` | 採る判定の絞り込み                 |
| `FR-PII-22` `FR-PII-22a` `FR-PII-22b`  | 実行する場所と、失敗したときの扱い |
| `FR-PII-23`〜`FR-PII-23e`              | モデルのファイルの配り方と置き場所 |

## 方式

**第 2 層は取りこぼしてよい。** 判定はモデルに依るもので、長い本文・分け方の正規化・
実行環境の違いなど、取りこぼす理由がいくつもある。全部を拾おうとして待たせたり、会話を
止めたりするほうが害が大きい。

**許さないのは 2 つだけである。**

| 許さないこと       | なぜ                                                         |
| ------------------ | ------------------------------------------------------------ |
| 誤って伏せること   | モデルが読む内容が変わる。取りこぼしと違い、あとから補えない |
| 黙って失敗すること | 画面が変わらないので、伏せているつもりで送り続ける           |

取りこぼしは、利用者が挙げる語と辞書（`FR-PII-03`）で補う。判定に時間がかかりすぎるときも、
そこまでの結果で先へ進める（`FR-PII-23f`）。

**ただし、辞書に無い氏名を伏せる手段はこの層しか無い。** 第 1 層は推定に頼る検出を持たない
（[pii-masking.md](pii-masking.md)）。モデルを置かない利用者は、氏名を辞書へ書くことになる。

| 決めごと                         | 理由                                                                                   |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| 判定はこの機械の中で実行する     | 判定には伏せる前の本文が要る。外部へ送ると、伏せる機能そのものが漏れの経路になる       |
| 確度で絞る                       | 誤って伏せるとモデルが読む内容が変わる。取りこぼしと違い、あとから補えない             |
| 位置を特定できない判定は採らない | 伏せるには本文の何文字目かが要る。推測で置き換えると、戻すときに別の文字列になる       |
| 第 1 層を優先する                | 第 1 層は形で判定していて確実である。重なったときに推定側を採る理由が無い              |
| 製品名は既定で伏せない           | `Docker` や `React` を伏せると、技術の話が読めなくなる。守るものも無い（`FR-PII-21b`） |
| モデルのファイルは同梱しない     | 配布物が 15 倍になる。閉鎖環境ではどちらにせよ手で運ぶので、同梱して得るものが無い     |
| 既定では実行しない               | 第 1 層と同じく、気づかないうちに送る内容が変わる状態を避ける（`FR-PII-21c`）          |

### 何を採るか

判定は 8 つの区分を返す。区分ごとに、伏せるかを切り替えられる（`FR-PII-21a`）。

| 区分    | 中身       | 既定 | 伏せ字の種類 |
| ------- | ---------- | ---- | ------------ |
| `PER`   | 人名       | 入   | `person`     |
| `ORG`   | 社名       | 入   | `org`        |
| `ORG-P` | 政治的組織 | 入   | `org`        |
| `ORG-O` | その他組織 | 入   | `org`        |
| `LOC`   | 地名       | 入   | `address`    |
| `INS`   | 施設名     | 入   | `org`        |
| `PRD`   | 製品名     | 切   | —            |
| `EVT`   | イベント名 | 切   | —            |

### 確度で絞る

判定には確度が付く。閾値に満たないものは採らない（`FR-PII-21d`）。既定は 0.9 とする。

実測では、電子メールの `taro@corp.example` が `PER` と `ORG` に割れて返った。確度は
0.25 と 0.34 で、閾値で消える。氏名・社名・住所の確度はいずれも 0.93 以上だった。

### 本文の位置を求める

判定が返すのは、分かち書きした断片とその区分だけで、**本文の位置が付いていない**。伏せる
には位置が要るので、断片を本文と先頭から突き合わせて求める。

区切りをまたいで繋がることがある。`佐藤。森さん` は `佐藤` `。` `森` が同じ区分で連続
して返り、そのままだと `佐藤。森` が 1 つの固有名詞になる。句読点と括弧で区切る。

求められなかった断片は採らない（`FR-PII-21e`）。推測して置き換えるより、伏せないほうが
被害が小さい。**ただし取りこぼしたことは件数に出す**（`FR-PII-22a`）。

### なぜ変換するのか

公開されているモデルは PyTorch の重みで、実行するには Python が要る。本製品は Node で
動くので、ONNX 形式へ直す。**これが必須の変換である。**

int8 への量子化は任意だが、1.03 GB が 265 MB に、1 回 44 ms が 21 ms になるため採る。

変換は配布の前に 1 回行う。利用者の側に Python は要らない。

手順は `scripts/build-ner-model.sh` に置いてある。この機械に Python は要らず、docker
だけで動く。作り直すときと、配っているファイルの元を確かめたいときに使う。

### 何を配るか

5 つのファイルで動く。`sentencepiece.bpe.model` は `tokenizer.json` と重複するので入れない。

| ファイル                    | 大きさ   | 役割                     |
| --------------------------- | -------- | ------------------------ |
| `onnx/model_quantized.onnx` | 265.4 MB | 判定するもの本体         |
| `tokenizer.json`            | 16.3 MB  | 文章を断片に分ける定義   |
| `config.json`               | 984 B    | 区分の名前（`PER` など） |
| `tokenizer_config.json`     | 1.2 KB   | 分け方の設定             |
| `special_tokens_map.json`   | 964 B    | 特殊な印の対応           |

**手順書ではなくファイルを配る。** 変換はバイト単位では再現しない。同じ元モデルでも、
変換する仕組みの版が違うと大きさがずれる（実際に他者の変換と 435 KB 違った）。
各自に変換させると、照合する値が決まらない。

### モデルの置き場所

配布物には入れない（`FR-PII-23`）。GitHub Release の添付として置く。

**拡張の版とは別のタグにする。** 同じタグに入れると、拡張の版を上げるたびに 282 MB を
取り直すことになる。

```
model-ner-ja-v1
  ├ ner-ja.tar.gz   5 つのファイルをまとめたもの
  └ SHA256SUMS      照合する値
```

置き場所は設定で指す（`FR-PII-23a`）。

**どこを見ているかを画面に出す。** 出さないと、閉鎖環境の利用者はどこへファイルを運べば
よいか分からない。欄を空にすると既定の場所を見るが、その場所は画面のどこにも書いていな
かった。いまは実際に見ている場所と、置かれているかどうかを出す。

```
モデルの置き場所
[                    ] [⤓ 取得]
見ている場所: /home/…/.agent/pii-ner
置かれていません（6 ファイルが足りません）
```

**照合はしない。** `SHA256SUMS` との突き合わせは 265 MB を読み直すので、画面を出すたびに
は実行できない。あるかどうかだけを見る。読み込む前の照合は別に行う（`FR-PII-23e`）。

| 環境     | どう置くか                                             |
| -------- | ------------------------------------------------------ |
| 網がある | 利用者が指示したときだけ取得する（`FR-PII-23c`）       |
| 閉鎖環境 | 同じ添付を別の機械で保存し、媒体で運ぶ（`FR-PII-23d`） |

**どちらも拡張から見れば同じである。** 置いてあるファイルを読むだけで、取得の有無は
関係しない。読み込む前に、`SHA256SUMS` と突き合わせる（`FR-PII-23e`）。

ファイルが無いときは、第 2 層が動かないだけで、第 1 層はそのまま動く（`FR-PII-23b`）。

## 制約

使うモデルは **`tsmatz/xlm-roberta-ner-japanese`** とする。XLM-RoBERTa（0.3B）を、
ストックマークの `ner-wikipedia-dataset` で学習したものである。分かち書きが
SentencePiece なので、MeCab や Juman++ を要求せず、Node だけで実行できる。東北大 BERT 系
と DeBERTa 系は分かち書きに外部の仕組みが要るため、採れない。

**Node では WASM を選べない。** `device` が受け付けるのは `cpu`（native）と `cuda` と
`webgpu` だけだった。したがって native の実行の仕組みを同梱することになり、**配布物は
platform ごとに分かれる**。

**配るのは Windows と Linux の x64 だけとする。** 利用者は自分の platform のぶんだけを
取るので、1 人あたりの大きさは変わらない。増えるのは版を出すときの手順である。

実測した大きさは次のとおりである。

| 中身                            | 大きさ   |
| ------------------------------- | -------- |
| モデル（int8）                  | 265.4 MB |
| 分かち書きの定義（`tokenizer`） | 16.3 MB  |
| 〃（`sentencepiece`）           | 4.8 MB   |
| 実行の仕組み（linux x64）       | 33.9 MB  |
| 〃（windows x64）               | 23.0 MB  |

実際に出来た配布物の大きさは次のとおりである。

| 配布物            | 大きさ  |
| ----------------- | ------- |
| 第 2 層を入れる前 | 19 MB   |
| linux-x64         | 31.9 MB |
| win32-x64         | 27.8 MB |

CUDA と DirectML の提供部は同梱しない。含めると 1 つで 302 MB になり、この用途では使わない。

実測した所要時間は次のとおりである（8 コアの CPU、短い議事録 1 本）。

| 方式 | 1 回あたり | 読み込み |
| ---- | ---------- | -------- |
| int8 | 21 ms      | 916 ms   |
| fp32 | 44 ms      | 1,971 ms |

int8 を既定とする。**速いうえに、確度の低い誤りがより低く出た。**

## 危険なところ

**位置の取り違えがいちばん危ない。** 判定は位置を返さないので、こちらで求める。同じ名前
が 1 つの文章に 2 回出ると、2 つ目を 1 つ目の位置として扱う誤りが起きやすい。求めた位置の
文字列が、判定した断片と一致することを毎回確かめること。

**閾値を下げると壊れる。** 確度を下げるほど取りこぼしは減るが、誤検出が入る。誤検出は
モデルが読む内容を変えるので、取りこぼしより害が大きい。下げる方向の変更は、実際の文書で
確かめてから行う。

**モデルが無い状態に気づけない。** ファイルを置き忘れると、第 2 層は黙って動かない。第 1 層
が動いているため、画面の見た目は変わらない。件数の提示（`FR-PII-22a`）はこの取り違えを
見つけるためにある。

**製品名を入にすると技術文書が壊れる。** `React` が伏せ字になると、モデルは何の話か
判断できない。切り替えられるようにはするが、既定は切のままにすること。

**配る platform を取り違えても気づけない。** `vsce package` は `vscode:prepublish` を
実行し直すので、束ねる段に渡した platform の指定が失われ、**いま動いている機械のもの**が
入る。Windows 向けに作ったつもりで Linux の native が入った。`package-vsix.mjs` が
環境変数で渡し直し、作ったあとに中身を確かめている。この確認を外さないこと。

### 手で確かめること

モデルのファイルを伴う経路は、自動の試験で触れない。版を出す前にこの 5 つを確かめる。

| 何を         | どう確かめるか                                                |
| ------------ | ------------------------------------------------------------- |
| 取得         | 設定の画面から取得を指示し、指した場所にファイルが並ぶこと    |
| 閉鎖環境     | 網を切り、手で置いたファイルだけで判定が動くこと              |
| 無いとき     | ファイルを消し、第 1 層だけで動き、その旨が出ること           |
| 配布物       | platform 別の VSIX を作り、自分の platform の分だけで動くこと |
| 本物のモデル | 実際のモデルを置いて判定し、範囲が本文と一致すること          |

## できていないこと

- 日本語だけを対象とする。英語の文章の中の固有名詞は、この層では判定しない。
- 学習に使われたのは Wikipedia の文である。社内の文書の書き方（表形式の議事録、箇条書き
  だけの記録）では、精度が下がる可能性がある。実際の文書で確かめていない。
- 確度の閾値は 1 つしか持たない。区分ごとに変えられない。
- 判定は 1 文ずつではなく、渡された文章をまとめて扱う。長い文章を渡したときの上限を
  決めていない。
- モデルの取得先は 1 つしか持たない。社内のミラーを指す設定は、置き場所の設定で代用する。
- GPU は使わない。CPU だけで実行する。
- macOS 向けには配らない。arm64 の実行の仕組みは 34.5 MB で用意できるが、確かめる環境が
  無い。要るようになったら配布の対象へ足す。
